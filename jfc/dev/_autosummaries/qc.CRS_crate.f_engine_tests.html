Exceptions

exception qc.CRS_crate.f_engine_tests.IterationTimeout

Raised when a single test iteration exceeds its allotted wall-clock time.

A frozen iteration is assumed to be caused by a hardware problem (the crate/board stops responding and a blocking call never returns). Rather than diagnosing it here, the watchdog aborts the stuck iteration so the test can power-cycle and continue with the next one.

Subclasses RuntimeError so it is caught by the existing broad except Exception handlers, while remaining distinguishable via isinstance(e, IterationTimeout).

exception qc.CRS_crate.f_engine_tests.PSUError

Raised for any PSU-related failure during crate power control.

Subclasses RuntimeError so that existing except RuntimeError handlers still catch it, while allowing callers to distinguish PSU failures from genuine FPGA programming / array-init errors via isinstance(e, PSUError).

iteration_watchdog(timeout, label='Operation')

Abort the enclosed block if it takes longer than timeout seconds.

This guards against hardware problems that freeze an iteration: when a board stops responding, a blocking call (e.g. asyncio.run(…) on an FPGA transaction) can hang forever and stall the whole test run. Simply measuring elapsed time after the fact cannot help, because control never comes back. Instead we arm a SIGALRM timer that fires while the blocking call is in progress and raises IterationTimeout from the signal handler, which unwinds the stuck call so the caller can move on to the next iteration.

Parameters:

  • timeout – Watchdog period in seconds. Values <= 0 (or None) disable the watchdog, preserving the previous behaviour of waiting indefinitely.

  • label – Optional text included in the exception message to identify which iteration timed out.

Yields:

None. Control returns to the caller with the watchdog armed.

Raises:

IterationTimeout – if the block is still running when the timer expires.

Notes

SIGALRM is Unix-only and can only be delivered to the main thread, which is how these QC tests are run (a CLI menu / plain pytest session). If the watchdog cannot be armed (non-main thread or a platform without SIGALRM) it degrades gracefully to a no-op and prints a warning rather than breaking the test. Resolution is 1 second, since signal.alarm() takes an integer.

test_adc_clocks(xr)

QC003: ADC clock test: ensure all ADCs get the correct clocks on every channel + power cycling between checks

Procedure:

  • Start the ADC clock test on the computer

  • Power up crate - Iterate through all clocks on all mezzanines on all motherboards, check that they are correct within some tolerance set in the config. - Repeat for desired number of cycles

  • Power off crate

test_init(xr)

QC001: Crate initialization test: ensure crate properly intializes

Procedure:

  • Start the crate init test on the computer

  • Power up crate

  • If init ok, test passed: - all 16 boards found in hwm - all FPGAs programmed - crate must sync

test_power_cycle(xr)

QC004: Power cycle test: cycle crate initializations, logging ADC clock and UDP errors.

Procedure:

  • Start the power cycle test on the computer

  • Power up crate

  • Cycle through crate initialization n_cycles times, count some relevant errors

  • Each iteration is guarded by a watchdog (iter_timeout in the config): a cycle that takes too long is assumed to be frozen by a hardware problem, is aborted, and the test moves on to the next one

test_ps_connection(xr)

QC000: Power supply connection test: ensure power supply responds to commands consistently.

Procedure:

  • Start the power supply connection test on the computer

  • Open connection to power supply

  • If test fails, then power supply stops turning on/off

test_sync(xr)

QC002: Sync/IRIG-B test: stress test of crate sync using IRIG-B

Procedure:

  • Start the sync test on the computer

  • Power up crate

  • After initializing crate, run self.ca.sync_async() in a loop, and only pass if it’s able to successfully sync N times (e.g. N = 100)
