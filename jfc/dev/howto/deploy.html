Code development and versioning guide

The main development branch, as of July 3, 2024 is the deploy branch. For synchronizing separate develoment efforts, all the new branches must be forked from deploy branch and, after implementing desired changes, merged back to deploy.

Development process

  1. Create a new branch from the latest commit on deploy branch.

  2. Make the desired changes.

  3. When developing, commit often and write concise commit messages - this will help other people debug the future compability problems.

  4. Run the necessary tests to make sure the code work for your target platform.

  5. [TBD] Run the tests to ensure there is no problems with other platforms.

  6. Important: If there are any new commits on deploy since your branch was created - merge deploy into your branch. This is needed to maintain synchronization between different development branches. Merging deploy into your branch may break the code, therefore you must re-run all available tests and fix the problems.

  7. Merge your branch into deploy.

  8. Push all the changes. You need to push changes before putting a tag, so the newest changes will appear in deploy. If you put a tag before pushing, the latest commit will not be added to deploy history.

  9. Put a tag on the new commit specifying the version and the target platform of the commit. This is needed to ensure you always get the working code for any platform, because in general the latest version of the deploy may not work on all platforms. See the versioning guide below.

  10. Push your tag to the remote by running git push origin deploy --tags.

Note: If you are in rush, you can skip steps 5-8 and put a tag on your branch - see the guide below.

Versioning guide

  1. The general format of the tag is x.y.z+[platform].[config]. The x, y and z are version numbers for major releases, minor releases and patches correspondingly. The [platform] should be a three-symbol word indicating the targed platform. For example, crs for CRS boards or ice for the ICE board. The [config] is the target configuration for which the code was tested. For example, co is for configurations that support on-board correlation and ct is for configurations that support corner-turn.

  2. The version number must always increase. For example, if the latest tag is 1.2.3+ice.co and you are deploying a crs.ct, your tag must be either 1.2.4+crs.ct if it is a small patch or 1.3.0+crs.ct if it is a significant change.

  3. If you are tagging a branch that is not deploy copy the latest tag on deploy, change the platform and the mode, and update the version number. Also, add the rc1 to the tag after the last number to indicate that this tag is release candidate. For example, if the latest deploy tag was 1.2.3+ice.co, you would change it to something like 1.2.4rc1+crs.ct.

    When merging your changes into deploy follow the regular procedure (steps 1-2) and increase the version number.

    Note: If you need to put several consecutive tags on your dirty branch - advance the number in the rc flag, e.g. rc2, rc3, etc. This number represents the increasing level of shame you accumulate before merging changes into the main branch.
