CRS backplane EEPROM (IPMI FRU) and discovery beacon mapping
=============================================================

Overview
--------

Each CRS motherboard reads a backplane FRU EEPROM over I2C when it boots.
The image follows the IPMI Platform Management FRU Information Storage
Definition (version 1).  U-Boot and TCPipe decode the same layout; host
tools (discover.py, crs_discovery.py) consume the data after it is
re-published in UDP discovery beacons.

Physical access
---------------

  Bus / alias : I2C0, device-tree alias ``backplane0``
  Address     : 0x50 (typical; see board device tree)
  Read path   : motherboard ARM (U-Boot at boot, TCPipe at runtime)
  Host access : TCPipe I2C0 @ 0x50 (see tests/crs_corr_tests/crs_bp_eeprom.ipynb)

Only the Board Information Area and Chassis Information Area are used.
The Product Information Area is normally absent on backplane EEPROMs.


IPMI FRU layout (areas used on the backplane)
---------------------------------------------

Common header (8 bytes)
  Offsets in the header point to areas in 8-byte units.  Only the board
  and chassis areas are decoded for CRS backplanes.

Board Information Area  — identifies the *backplane segment* (CBP)
  Standard IPMI field order (type/length ASCII strings after a 6-byte prologue):

    Field  IPMI name        Beacon field             Example value
    -----  ---------------  -----------------------  -------------------------
    1      Manufacturer     Backplane Manufacturer   t0.technology
    2      Product Name     —                        4-slot backplane
    3      Serial Number    Backplane Serial         069
    4      Part Number      Backplane Model          4SBP
    5      FRU File ID      —                        (optional; often empty)
    6+     Custom fields    (see below)              revision=1, slot=3

  Product Name is decoded by firmware but is not a separate discovery-beacon
  header; the beacon carries Part Number as Backplane Model (default ``CBP``
  when the part field is empty but serial is present).

  Board-area custom field convention (t0 CRS):
    revision=N   — backplane segment hardware revision (Backplane Revision).
    slot=N       — board position on the 4-slot backplane segment (1–4,
                   Backplane Slot).  IPMI has no dedicated slot field; these
                   are extra 8-bit ASCII type/length fields after FRU File ID,
                   before the area terminator (0xC1).

  Example board-area custom fields (ASCII, as stored in the FRU):
    revision=1
    slot=3

  A crate is built from several 4-slot backplane segments.  Each segment
  has its own board-area serial (e.g. SN0069).  Boards in the same
  segment share that serial.

Chassis Information Area  — identifies the *crate* (CCR) and crate-wide slot
  Standard IPMI field order (after a 3-byte prologue: version, length,
  chassis type):

    Field      IPMI name        Beacon field       Example value
    ---------  ---------------  -----------------  -------------------------
    (prologue) Chassis Type     Crate Revision (*) IPMI chassis-type code
    1          Part Number      Crate Model        CCR
    2          Serial Number    Crate Serial       0011
    3+         Custom fields    Crate Slot         slot=15

  (*) Chassis Type is an IPMI type code, not a product revision string.
  It may be published as Crate Revision when a numeric revision is added to
  the beacon format.  Crate Manufacturer is not a standard chassis-area
  field; when present in beacons it is supplied by firmware convention.

  Chassis-area custom field convention (t0 CRS):
    slot=N   — physical slot of this CRS board in the full crate (1-based,
               1–16, Crate Slot).  Parsed by looking for the prefix ``slot=``.

  All boards plugged into the same crate read the same chassis part/serial.
  The chassis ``slot=N`` custom field is written per board location when the
  backplane EEPROM is programmed.

  Legacy EEPROMs stored the only ``slot=N`` field in the chassis area.
  Current firmware still publishes that value as ``Backplane Slot`` in the
  UDP beacon.  New images should move backplane segment slot and revision
  into board-area customs (above) and reserve chassis ``slot=N`` for the
  crate-wide Crate Slot.


Firmware decode (U-Boot / TCPipe)
---------------------------------

Both firmware stacks parse the same FRU layout.

U-Boot (t0_backplane.c) populates environment variables at boot:

  IPMI field (area)              U-Boot env variable
  -----------------------------  --------------------------
  Board Manufacturer             backplane_manufacturer
  Board Product Name             backplane_product
  Board Serial Number            backplane_serial
  Board Part Number              backplane_part
  Board custom ``revision=N``    backplane_revision (target)
  Board custom ``slot=N``        backplane_slot (target)
  Chassis Type                   crate_type
  Chassis Part Number            crate_part
  Chassis Serial Number          crate_serial
  Chassis custom ``slot=N``      crate_slot (target) / backplane_slot (legacy)

TCPipe (tcpipe.c / ipmi.c) stores the same information in ``hw_info``:

  IPMI field (area)              TCPipe hw_info member
  -----------------------------  --------------------------
  Board Product Name (*)         bp_part
  Board Serial Number            bp_serial
  Board custom ``revision=N``    bp_revision (target)
  Board custom ``slot=N``        bp_slot (target)
  Chassis Part Number            crate_model
  Chassis Serial Number          crate_serial
  Chassis custom ``slot=N``      crate_slot (target) / bp_slot (legacy)

  (*) If Product Name is empty, Part Number is used instead.

  Target behaviour: read ``revision`` and segment ``slot`` from board-area
  customs first; use chassis ``slot=N`` only for crate-wide Crate Slot.
  Until EEPROM images and firmware are updated, chassis ``slot=N`` alone is
  still accepted and is published as ``Backplane Slot`` in the beacon.


UDP discovery beacon mapping
----------------------------

Boards periodically broadcast FWREQ/1 (U-Boot) or TCPIPE/1 (TCPipe) UDP
beacons on port 9875.  Header names are case-insensitive; Python normalizes
them to lowercase with hyphens (e.g. ``Backplane Serial`` -> ``backplane-serial``).

Discovery beacon fields (target layout)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

  Motherboard (from motherboard FRU / U-Boot env — not backplane EEPROM):

    Manufacturer: t0
    Product: crs
    Revision: 5
    Serial: 0216

    Bootloader: u-boot
    Bootloader Version: 0.1          See Note 1

  Backplane segment (from backplane EEPROM — See Note 2):

    Backplane Manufacturer: t0
    Backplane Model: CBP
    Backplane Serial: 085
    Backplane Revision: 1
    Backplane Slot: 3

  Crate (from backplane EEPROM chassis area + firmware):

    Crate Manufacturer: t0
    Crate Model: CCR
    Crate Serial: 011
    Crate Revision: 1
    Crate Slot: 15

  Note 1 — Bootloader Version identifies the running ARM image (U-Boot or
           TCPipe build).  Host tools use it to decide whether a firmware
           upload is required.

  Note 2 — All Backplane * headers are sourced from the backplane FRU board
           information area (standard fields and board-area custom fields).
           Backplane Revision and Backplane Slot use board-area customs
           ``revision=N`` and ``slot=N`` (segment position 1–4).  Crate Slot
           uses the chassis-area custom ``slot=N`` (crate position 1–16).
           Current U-Boot FWREQ/1 beacons send only Backplane Serial and
           Backplane Slot (legacy mapping from chassis ``slot=N``); the other
           Backplane * headers appear in the target layout and in TCPIPE/1
           (partially — see table below).

Mapping table — beacon header -> IPMI source -> Python (CRSBeacon)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

  Beacon field             IPMI / source                       U-Boot FWREQ/1   TCPIPE/1 today     Python field(s)
  -----------------------  ----------------------------------  ---------------  -----------------  ---------------------------
  Manufacturer             Motherboard FRU                     yes              yes                (board identity)
  Product                  Motherboard FRU                     yes              yes                board-part
  Revision                 Motherboard FRU                     yes              yes                fields["revision"]
  Serial                   Motherboard FRU                     yes              yes                board-serial
  Bootloader               firmware                            yes              yes                fields["bootloader"]
  Bootloader Version       firmware build ID                   yes              yes                fields["bootloader-version"]

  Backplane Manufacturer   Board Manufacturer                  no               no                 —
  Backplane Model          Board Part Number                   no               Backplane Part (*)   backplane-part
                                                                                (name legacy)        backplane-model
  Backplane Serial         Board Serial Number                 yes              yes                backplane-serial
  Backplane Revision       Board custom ``revision=N``         no               no                 —
  Backplane Slot           Board custom ``slot=N`` (target);   yes              yes                backplane-slot
                           chassis ``slot=N`` (legacy)                                          (becomes beacon.slot)

  Crate Manufacturer       (target; not in chassis FRU)        no               no                 —
  Crate Model              Chassis Part Number                 no               Crate Model        crate-part
                                                                                                    crate-model
  Crate Serial             Chassis Serial Number               yes              yes                crate-serial
  Crate Revision           Chassis Type (target mapping)       no               no                 —
  Crate Slot               Chassis custom ``slot=N`` (target)  no               no                 crate-slot

  (*) TCPIPE/1 currently emits ``Backplane Part``; the target name is
      ``Backplane Model``.  Value comes from board Product Name if set,
      else Part Number, with default ``CBP`` when only serial is known.

Notes on beacon defaults
~~~~~~~~~~~~~~~~~~~~~~~~

  TCPipe ``beacon_part_or_default(part, serial, default)`` supplies:
    CBP  when backplane serial is known but part/model is missing
    CCR  when crate serial is known but part/model is missing

  discover.py uses the same display defaults (CBP / CCR) when formatting
  the live table, even if the raw beacon omitted the part headers.

  U-Boot FWREQ beacons are minimal: they include Backplane Serial, Crate
  Serial, and Backplane Slot only.  Crate model and backplane model are
  read from EEPROM into U-Boot env but are not yet placed in the UDP
  packet.  Host-side crate matching that requires both model and serial
  therefore fails against FWREQ beacons until boards run TCPIPE or U-Boot
  is extended.


Example
-------

  EEPROM chassis area : Part "CCR", Serial "0011", custom "slot=15"
  EEPROM board area   : Product "4-slot backplane", Serial "069", Part "4SBP",
                        custom "revision=1", custom "slot=3"

  TCPIPE/1 beacon (excerpt, current on-wire names):
    Manufacturer: t0
    Product: CRS
    Revision: 5
    Serial: 0167
    Bootloader: tcpipe
    Bootloader Version: <git-version>
    Backplane Part: 4-slot backplane
    Backplane Serial: 069
    Backplane Revision: 1
    Backplane Slot: 3
    Crate Model: CCR
    Crate Serial: 0011
    Crate Slot: 15

  discover.py columns (target):
    backplane : CBP SN0069
    crate     : CCR SN0011
    slot      : 15   (crate slot; from chassis custom or beacon Crate Slot)

  FPGAArray / crs_discovery hardware map:
    CRSBackplane(serial='0011')   from crate headers
    CRS motherboard(serial='0167', slot=15, crate=...)  from crate slot headers
